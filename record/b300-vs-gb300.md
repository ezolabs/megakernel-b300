# NVIDIA built the megakernel for GB300. We run it on plain B300, which it did not support.

**The short version.** NVIDIA's low-latency megakernel for DeepSeek-V4.1-Flash (`sgl-nvidia-mega`, published
through SGLang/LMSYS on 2026-10-18) was written, tuned and measured on **4× GB300** — Grace-Blackwell
superchips in NVIDIA's own NVL72 rack. Its shipped code required **152 SMs per GPU**. We serve on rented
**4× B300 HGX** boxes: the same Blackwell Ultra GPU family (sm_103), but **148 SMs per GPU** on an **x86** host
with no Grace CPU. As shipped, the plugin's requirements gate refused the B300 outright. We patched it, built a
safety layer around it, measured it more widely than NVIDIA published, and have served production traffic on it
since 2026-10-30. Upstream added an opt-in 148-SM profile only afterwards (plugin PR #35, merged 2026-10-30 20:12Z),
and its B300 speed claim covers one request only.

All "ours" figures are cited to the record in this repo; every NVIDIA/upstream figure is cited to its public URL
with the date we read it (2026-10-31). Where conditions differ, the table says so.

## 2. Why plain B300 was not supported, and what we changed

### The hardware difference

| | GB300 (NVIDIA's target) | B300 (ours: box-a, box-b) |
|---|---|---|
| SMs per GPU | 152 — the plugin's shipped floor: "the GEMM pair's persistent schedule and the Lamport consumer stay within GB300's 152 SMs" (`resident_blocks=152`) | **148** (`fleet-history/box-a/README.md` hardware table) |
| GPU | Blackwell Ultra, sm_103 | B300 SXM6 (AC on box-a, PC on box-b), sm_103, cc 10.3, 275,040 MiB, 1,100 W limit, 2,032 MHz SM clock |
| host CPU | Arm Grace, in the same tray | x86: 2× Intel Xeon 6776P (box-a), AMD EPYC 9575F (box-b) |
| GPU interconnect | NVLink 5 (NVL72 rack) | NV18 between every pair, P2P ~770 GB/s (box-a bring-up) |
| where | NVIDIA's own nodes, huge pages gated free | rented containers, shared-memory transparent huge pages off (`transparent_hugepage/shmem_enabled` is `never`, `box-c/qa/box-a-tuning-20261026/raw/rec/boot-B9.txt`) |

The plugin's persistent GEMM schedule and its cross-block (Lamport) consumer were sized to keep 152 blocks
resident, one per GB300 SM (the spec's own comment, quoted above). Its requirements check (`resident_blocks=152`)
is a startup gate: the plugin README states that listing `sm148` "admits the 148 SMs of a B300 instead of the 152
required otherwise", and that an unsupported setup stops at startup rather than falling back ("No silent
fallback"). As shipped before PR #35 there was no `sm148` option, so a B300 could not pass the gate. (The record holds
no boot of the unpatched plugin on B300: the refusal is the plugin's documented behaviour, not an error we logged.)

### What we changed (the B300 patch)

`fleet-history/box-a/sgl-nvidia-mega-b300-spec.patch` (applied on plugin main `54b4289`; verified on
the box as `plugin deepseek_v41 API_VERSION 2 resident_blocks 148 features ['KV_OFFLOAD', 'SPECULATIVE_DECODING']`,
`box-c/qa/box-a-megakernel-20261029/raw/build-latest/verify.log`):

1. `resident_blocks=152` → `148` ("GB300 floor 152 → B300 148", marked unofficial).
2. `Feature.KV_OFFLOAD` added to the spec's features, so the megakernel engine accepts our hierarchical KV cache
   (HiCache host offload with `direct` / `page_first_direct` I/O). Upstream's GB300 configuration runs without it.

Other things the plain upstream recipe did not give us on this box, all in the record:

- **API version gate.** Plugin `54b42892`+ speaks megakernel API v2; our serving trees were v1, and a v1 SGLang
  given a v2 plugin **boots silently without the megakernel** ("uses megakernel API version 2; this SGLang requires
  version 1") — no error, just the old speed. We merged upstream to a v2 tree (at or past `8f1b7691ca`) and the
  gate checks that the megakernel's decode graphs were captured (27/27 target decode graphs, batch 1–64, in the
  config X' gate) (`fleet-history/box-a/RETRY-MEGAKERNEL.md`,
  `box-c/qa/prod-merge-20261030/raw/gate/NOTES.md`).
- **EP1 is forced.** The plugin requires `--ep-size 1`, costing 25.2% of the KV pool on B300 (66.65 M → 49.88 M
  tokens) and accounting for all of the teacher-forced drift (`megakernel.md`).
- **The slot trap in upstream's later fix.** PR #35's `SGLANG_NVIDIA_MEGAKERNEL_SLOTS=sm148` *replaces* the 39
  shipped slots rather than adding to them, so `SLOTS=sm148` alone boots an engine that runs stock code every step
  (`box-c/qa/box-a-megakernel-20261029/README.md` "Plugin"; `box-c/qa/sglang-sweep-20261031/NOTES.md` §2).
- **Host-CPU bound scheduler.** On box-a's host only 16 of 128 cores turbo to 4,600 MHz (the rest 2,300 MHz);
  pinning the scheduler to them took the C1 step from 7.06–7.15 to 5.40–5.49 ms (+20–24% tok/s) before the
  megakernel (`box-c/SPEED-REGISTER.md` SR-051). A Grace host has no such split.

### The safety layer (ours; not in the plugin)

| piece | purpose | source |
|---|---|---|
| TP-consistency probe (`SGLANG_MK_TP_PROBE=1`, every 100 steps serving / 10 in soaks, `ASSERT=1`) | ranks compare step state; a desync fail-stops instead of hanging | `box-c/qa/box-a-megakernel-20261029/merge-latest.md` |
| `hangwatch.py --service --on-hang kill` + `watchdog.sh` | a stalled engine is killed and relaunched with prewarm | `box-c/qa/box-a-megakernel-20261029/README.md` "Hangs" |
| router liveness test | a TP rank frozen 9.9 s: backend DOWN on every router pod in ≤ 5.6 s, streams paused and finished | `box-c/qa/box-a-megakernel-20261029/raw/box-a-return/NOTES.md` |
| full numerics + quality gate before every engine change | greedy, teacher-forced KL, NVIDIA's KL test, DSML tool-calls, gsm8k, L3a sign-off | `quality.md` |

### Upstream caught up afterwards

Plugin PR #35 (merged 2026-10-30 20:12Z as `b61745e`): listing `sm148` makes `resident_blocks()` return 148. Its
draft (10-30 06:25Z) required `max-running-requests=1`, a batch-1 decode graph and DSpark block 5; the merged form
dropped the cap, and upstream's own B300 evidence is one-request speed plus a GSM8K canary at client concurrency
12/16 with decode graphs to batch 16. Our patch predates it (applied 10-28 on plugin `39595061`, and 10-29 on
`54b4289`), is unconditional, and our evidence covers C1–C16 at `max-running-requests 64`. `b61745e` still lacks
`KV_OFFLOAD`. It "lowers only the 152 → 148 SM gate, which our B300 patch already does … Kernels are unchanged",
so we skip it until the next plugin bump (`box-c/SGLANG-UPDATES.md` "2026-10-31: read-only sweep of #38565 and
`sgl-nvidia-mega` #35"; `box-c/qa/sglang-sweep-20261031/NOTES.md` §2; `fleet-history/box-a/RETRY-MEGAKERNEL.md`).

## What not to claim

- Not "faster than GB300". The absolute single-request figures are close (our p90 954 vs their 928–946 tok/s),
  but the workloads, weights, acceptance and statistics differ; the honest statement is *the same relative gain,
  reproduced on hardware the code was not written for*.
- Not "NVIDIA's code is broken on B300". The gate refused B300 on purpose; we changed the gate and took
  responsibility for the result with our own tests.
- The B300 patch is unofficial; upstream's later `sm148` opt-in is the supported route and has not been adopted here
  yet.
